# StudyDate ID Beta RC — 25 August 2026

This note records the repository-side Beta RC hardening completed for the First Meet test cohort. It is a source-release record, not evidence that the production Supabase or Vercel state has already been changed.

## Included source changes

- Anonymous Chat supports Unicode emoji and a small allowlisted set of official StudyDate mascot stickers.
- Sticker messages share the existing conversation authorization, blocking, moderation, rate-limit, read-state, and privacy boundaries.
- Anonymous Chat polling is adaptive, pauses when the tab is hidden or the browser is offline, and resumes after connectivity returns.
- The open conversation marks newly received counterpart messages as read.
- The composer supports Enter to send and Shift+Enter for a newline while preserving IME composition.
- Campus Event QR scanning can request same-origin camera access through the application Permissions Policy. Microphone, geolocation, and payment permissions remain disabled globally.
- Production responses add HSTS while retaining the existing no-sniff, framing, referrer, API no-store, and robots boundaries.
- Product and engineering documentation now describes Event v2 as repository-implemented until the remote migration/deployment state is explicitly verified.
- Early Access now uses one moderation queue: Owner has full access, Staff review is an explicit least-privilege capability, approval sends a branded one-time invitation, claim is approved-only, then onboarding continues. Early Access approval stays separate from Student/Alumni Verification.

## Database change requiring preflight

The repository adds:

- `supabase/migrations/202608250001_anonymous_chat_official_stickers_v1.sql`
- `supabase/migrations/202608250002_early_access_moderation_invitation_v1.sql`

`202608250002` must be applied **before** deploying the app code in this RC. The public student magic-link endpoint calls the new service-role-only `can_issue_student_magic_link` RPC and intentionally fails closed if the database contract is unavailable.

Before any remote database mutation:

1. Verify the linked Supabase project name, reference, and organization.
2. Run `npx supabase migration list` and compare local and remote history.
3. Review the exact pending migration set. Do not assume only the sticker migration is pending.
4. Apply changes only after the migration plan is understood and approved.
5. Repeat the migration list and relevant live A/B tests after the push.

The sticker client is rolling-deploy tolerant: message listing falls back to the legacy RPC when the v2 RPC is not available yet. The migration is still required before sticker sending is considered enabled in the deployed product.

## Local release verification

Use Node.js 22.6 or newer for the repository test tooling. Restore the repository's official `package-lock.json` from the GitHub `main` branch when it is not present in a transferred source archive, then run:

```bash
npm ci
npm run verify:release
```

`npm run verify:release` runs lint, TypeScript type checking, all Node test suites, and the production Next.js build.

Browser/live audits are separate because they require a running application, valid environment configuration, browser state, or controlled test accounts. Run the feature-specific live/browser audits required for the release being deployed.

- The Node test runner discovered 308 tests: 284 passed and 24 test files could not start because this isolated environment lacks installed third-party packages (`zod` for 20 files, `lucide-react` for 2, and `sharp` for 2). There were zero assertion failures among tests that could run.

This avoids silently inventing a dependency tree when registry access is unavailable.

## Beta release boundaries

This Beta RC intentionally does **not** introduce a last-minute realtime database migration, Telegram discovery bot expansion, or a new account-eligibility model. Those changes require their own architecture, safety, migration, and rollout work after the controlled First Meet beta.

Do not label this source archive production-ready until dependency-backed verification, remote migration preflight, deployment checks, and controlled live tests are complete.
